# Security and privacy boundary

`@ckb-ccc/stealth` is a local, unaudited package prototype. Its current boundary is local derivation, recognition of supplied fixtures, ownership checks, and unsigned CCC outputs. A complete live testnet send/scan/spend lifecycle, independent security review, and upstream CCC acceptance have not been demonstrated. Public fixture keys must never receive assets of value.

## What stealth addresses protect

A one-time destination aims to obscure the relationship between a payment and the recipient's published identity. It does not establish anonymity. The demo's deliberately public keys provide no secrecy.

| Property | Boundary |
| --- | --- |
| Recipient identity | The reusable recipient meta-address is absent from the derived output lock. A matching view key can recognize the output. |
| Amounts and sender inputs | Public; neither is hidden by this package. |
| Ephemeral key | Public in the lock arguments. It is not the private ephemeral scalar. |
| Fresh change | Reduces address reuse; amounts, output relationships, fees, timing, network observations, and graph correlations remain visible. |
| View key | Recognition authority, not spending authority. Disclosure can expose recognizable payment history. |
| Spend key | Combined with the view key, enables derivation of one-time spending material. Disclosure can endanger funds; loss of required secrets can prevent recovery. |

## What runs locally

- [Meta-address decoding](../packages/stealth/src/meta-address.ts) checks the existing raw 66-byte representation and valid compressed curve points. This format has no checksum; syntactic validation does not detect substitution with another valid recipient.
- [Sender derivation](../packages/stealth/src/derivation.ts) uses fresh CSPRNG ephemeral scalars. Deterministic derivation and public identities are confined to the explicit [testing entry point](../packages/stealth/src/testing/index.ts); they must not be used as secret material.
- [Scanning](../packages/stealth/src/scan.ts) recognizes supplied, explicitly simulated records using a view key and spend public key. It validates the configured lock, encoding and capacity, rejects malformed or duplicate records, and excludes non-matches. Recognition proves no chain inclusion, confirmation, or live-cell status.
- [Spend-key derivation](../packages/stealth/src/spend.ts) checks the complete configured lock and derived public-key hash before returning sensitive material. A view key alone cannot authorize spending. The low-level return value must not enter logs, telemetry, screenshots, URLs, or ordinary UI state.
- [Transaction helpers](../packages/stealth/src/transactions.ts) build actual unsigned CCC outputs and check that a spend's change meta-address belongs to the supplied keys. Spend preparation returns public information and fresh destinations; it neither constructs a live input nor consumes a cell. Broadcast explicitly fails closed.

The application remains responsible for its CCC client, network, wallet, and operation approval. Local checks do not replace that approval or CKB consensus.

## Lock compatibility and signing remain open

The [configured lock](../packages/stealth/src/constants.ts) comes from inspected source. The [package provenance](../packages/stealth/README.md#source-provenance-and-compatibility-limits) records the upstream commits and hashing/argument format. Comparing source and locally generated bytes does not independently verify the deployed binary, cell dependency, announcement format, or a successful transaction.

The inspected stealth lock checks a **65-byte recoverable signature over the raw transaction hash** (`load_tx_hash()`). This differs from standard CKB sighash witness processing. A standard secp256k1 signer must not be assumed compatible. A reviewed lock-specific signer, verified dependencies, and real testnet execution are pending; this prototype does not produce signature witnesses.

## Checks required before live integration

These are outstanding acceptance conditions, not implemented guarantees.

| Boundary | Required check |
| --- | --- |
| Deployment and witness | Independently verify network, code hash, hash type, cell dependency, argument and announcement formats, and exact signing/witness behavior. |
| Chain discovery | Validate candidate records against canonical-chain context and live-cell status; account for omitted or stale records, rescans, confirmations, and reorganizations. |
| CCC completion | Inspect the final recipient, amount, network, dependencies, and fresh-change destination after input/fee completion and before approval. |
| Secret handling | Keep real view and spend secrets out of public services and evidence; isolate signing material and preserve fresh randomness. No custody or recovery system is implemented here. |
| Client and delivery | Treat a compromised frontend, dependency, host, or wallet environment as capable of leaking secrets or substituting transactions. Consensus cannot prevent secret exfiltration. |
| Evidence | Preserve visible `SIMULATED` labels. Display hashes, confirmations, block heights, and explorer evidence only when obtained from independently checked chain activity. |

Mainnet use, guarantees of anonymity, and assets of value are outside this prototype's current scope. Historical deployments or images do not establish that this CCC integration works on-chain.

## Review evidence

The [package tests](../packages/stealth/test/stealth.test.mjs) cover an independently generated frozen vector, malformed encodings and points, wrong ownership keys, mutated locks, capacity boundaries, fresh change, unsigned CCC serialization, unavailable live broadcast, and the public/testing export boundary. These checks exercise local algorithms and API behavior, not CKB-VM execution or an audit.

See [validation](validation.md) for executed checks, [status](status.md) for implemented and pending capabilities, and [research](research.md) for source evidence and open integration questions.
